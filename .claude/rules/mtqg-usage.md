# mtqgの使い方（このリポジトリでは最初から）

作業の中で生まれる「気づき・やること・質問と答え・不具合とそのやり取り・用語の合意・この先も効き続ける決まり事」を、コードと同じgitリポジトリの中に追記だけで残すツール。使い方の詳細は`mtqg`自身の`.mtqg/SCHEMA.md`（データ形式）と`mtqg --help`（コマンド）を見る。

このリポジトリは、自身の開発過程を最初から`.mtqg/`に記録する（mtqgリポジトリの段階4からの運用を、最初から採用した）。**`PLAN.md`は使わない。`mtqg context`が唯一の一次情報**であり、これだけでこのリポジトリの現状・次にやることが分かる状態を保つ。

記録に使う`mtqg`は、`.devcontainer/postCreate.sh`が`@latest`で入れる（ほかの道具と同じ）。この拡張が対応する最低の版は、それとは別に固定している（`src/mtqg/availability.ts`の`MIN_SUPPORTED_MTQG_VERSION`、`.claude/rules/mtqg-cli.md`「版」）。CIは、最低の版と`@latest`の両方で試す（2026-10-15、人間の決定）。

## 記録者

`.claude/settings.json`の`env`に`MTQG_AUTHOR_KIND=ai`・`MTQG_AUTHOR_NAME=claude-code`を設定済み。コマンドの前に明示しなくても、このリポジトリでのmtqgコマンドは記録者`ai`/`claude-code`になる。人間が記録するときだけ、`.claude/settings.json`の値を上書きするよう明示して呼ぶ（例：`MTQG_AUTHOR_KIND=human MTQG_AUTHOR_NAME=amisonnet8 mtqg r add "..."`）。

## 何をどの種類で記録するか

mtqg本体の運用（mtqgリポジトリ`.claude/rules/mtqg-usage.md`）と同じ考え方。

| 種類 | 例 |
|---|---|
| `m add`（memo） | 実装しながらの気づき、後で見返したい観察。**不具合はここに書かない**（下の`b add`を見る） |
| `t add`（todo） | やること。**着手前に立てる**（「後でまとめて」にしない。小さな作業でもよい）。**終わったら間を置かず`t done`にする**（開いたままにしない） |
| `q add`（question） | 判断に迷って人間に確認したいこと。**設計や実装に関わる質問は、聞き方（チャットでの一言、`AskUserQuestion`、プランモード中の確認など）を問わず必ず`q add`で記録する。** `AskUserQuestion`で人間に聞いたときは、その場で質問と回答を`q add <id> <回答>`まで記録する |
| `b add`（bug） | 見つけた不具合とそのやり取り。**判定基準：「本来動くべきものが動いていなかった」「仕様と実装がずれていた」はbug、単なる気づき・設計判断はmemo。** その場で直したものも含めて記録する（**「直したから」は判定基準に入らない**） |
| `g add`（glossary） | 用語の合意 |
| `r add`（rule） | 読めばそのまま従える決まり事 |

## このPJと関係のないことは記録しない

**このPJの`.mtqg/`には、このPJの作業だけを記録する。** 同じコンテナ・同じ会話で頼まれた、別のPJ・別のリポジトリ・道具そのものの作業は、このPJの記録に混ぜない。混ぜると、`mtqg context`がこのPJの現状を示さなくなり、人間もAIも作業を取り違える。

- 例：このPJのAIが、別のPJ（srwr・テンプレート・ほかの兄弟PJ）の修正や調査を頼まれたとき。その作業の記録は、**そのPJ自身の`.mtqg/`**（`cd`してから`mtqg`を動かす）に書く。記録先が無い・迷うときは、記録せずに会話で報告する
- 例：このPJが使う道具（qsoku・mtqg・srwr・bcuz・Trivy）の不具合を見つけたとき。このPJの動作に影響する範囲（回避策・版の注意）だけを、このPJに`m add`する。道具そのものの不具合の追跡は、道具のリポジトリで行う
- 記録する前に確かめる：**「このPJのコード・文書・設定・決まり事の話か」**。違えば、このPJには書かない
- コミットも同じ。別のPJの変更を、このPJのコミットに混ぜない（`git add`はパスを指定する）

## 作業を始めるとき

- `mtqg context`を読む。ここが現状・今後の一次情報（mtqgリポジトリと違い、`PLAN.md`にも過去の経緯にも頼らない）

## こまめに記録する

**`mtqg context`だけで、このリポジトリの現状と次にやることが分かる状態を保つ。**

- **todoは着手前に立て、終わったらすぐ`t done`にする。** まとめて書く・まとめて閉じる、をしない。開いたままのtodoは「今も残っている作業」として信用されるので、終わったのに開いたままだと現状を誤らせる
- **区切り（1つの変更、1つの決定、1つの確認が付いたところ）ごとに、その場で`m add`する。** セッションの終わりにまとめて数件書くのではなく、都度書く
- **人間に委ねる判断は`q add`でも開けておく**
- 何を記録すべきか迷ったら、**「これを書かずにセッションが終わったら、次のセッション（または人間）は`mtqg context`だけで気づけるか」**で判断する

## docs/design/との役割分担（決定、2026-09-28。2026-10-16 に共通のルールに合わせて改めた）

`docs/design/`（`vscode-extension.md`）は**今の設計**を保つ。経緯は、**前のやり方に戻すと同じ問題がまた起きるもの**だけを数行で書き、詳しいやり取りはmtqgのID（`q`・`m`）で指す（`.claude/rules/documentation.md`「`docs/design/`に書く経緯」）。それ以外の経緯（日付ごとの流れ、やり取り、修正の履歴、todo・bugの進み、「最初はXにしたがYと指摘されZに直した」のような narrative）はここに書かず、`.mtqg/`（`m add`・`q add`・`b add`）にだけ記録する。理由：経緯の一次情報はmtqgの journal で、design docにも同じ経緯を書くと二重管理になる（`.claude/rules/mtqg-cli.md`「解釈はコアの1か所に集める」と同じ考え方）。ただし、戻すと問題が再び起きる選択の理由は、今の設計を読む人が知らないと同じ誤りをするので、design docに残す

## その他

- `.mtqg/.local/`はコミットされない
- `.mtqg/`の中のファイルを直接編集しない（すべてmtqgのコマンド経由）
- mtqgはgitに対して読むだけ（コミット・push・設定の変更をしない）
- **手でmtqgに記録するときは、MCPツール（`mcp__mtqg__*`）を使う。** Bashから`mtqg`を呼ぶ場合（`bcuz "記録" mtqg …`、`.claude/rules/bcuz-usage.md`）、`--json`等のフラグは動詞の直後・本文（位置引数）より前に置く。本文の後ろに置くと、`--json`がフラグとして認識されず本文の一部としてそのまま記録されてしまう（例：`mtqg memo add "本文" --json`だと本文が`"本文 --json"`になる）。過去に7件＋3件がこの形で混入した（bug`9e399b09ef`、mtqg edit経由で修正済み）
